title: "Health endpoints"
description: "The liveness and readiness probes, and which one to point a monitor at."
---

The backend answers four health routes. None of them needs a token, so a kubelet, a load
balancer or an uptime monitor can call them directly.

| Route | What it checks | Answers |
| --- | --- | --- |
| `GET /health` | Nothing: the process is up | `200` `{"status": "ok"}` |
| `GET /health/live` | Nothing: the process is up | `200` `{"status": "alive", "service": "th2agent"}` |
| `GET /health/ready` | The database and the encryption key | `200` when both pass, `503` otherwise |
| `GET /health/notifier` | The mailbox that sends system emails | `200` when it works, `503` when it does not |

`/health` and `/health/live` both stay `200` as long as the server process runs, whatever
state its database is in. That is deliberate: a probe that restarts the server when the
database blips turns a short outage into a longer one.

## Readiness

`/health/ready` runs two checks and reports each one.

- **database**: runs `SELECT 1` through the application's database session. The check is
  bounded by a 2 second timeout, so a database that hangs fails the probe instead of
  holding it open.
- **fernet**: confirms that `ENCRYPT_KEY` is set and loaded. Without it the server cannot
  decrypt stored integration tokens. The server also refuses to start without a valid key,
  so on a deployment that booted this check is always `ok`. See
  [Configuration](/configuration).

When both pass, the answer is `200`:

```json
{
  "status": "ready",
  "checks": {
    "database": { "ok": true, "error": null },
    "fernet": { "ok": true, "error": null }
  }
}
```

When either fails, the answer is `503` and the body lists every check, so you can see
which one failed:

```json
{
  "detail": {
    "status": "not_ready",
    "checks": {
      "database": { "ok": false, "error": "database check failed" },
      "fernet": { "ok": true, "error": null }
    }
  }
}
```

The `error` strings you can get are:

| Check | `error` | Meaning |
| --- | --- | --- |
| `database` | `database check failed` | The query did not run. The cause is in the server log, not in the response, because the route is public and a raw database error can carry host names. |
| `database` | `timeout after 2.0s` | The database did not answer within 2 seconds. |
| `fernet` | `ENCRYPT_KEY not configured` | No encryption key was loaded. The server does not start in that state, so you will not normally see this one. |

## Notifier

`/health/notifier` reports whether the mailbox that sends system emails can still do so.
It answers `503` with `"status": "degraded"` when the shared mailbox's owner integration is
missing or revoked, because system emails would fail. With no system mailer configured,
it answers `200` and says so:

```json
{
  "status": "ok",
  "healthy": true,
  "configured": false,
  "owner": "",
  "detail": "system mailer not configured (NOTIFICATION_INTEGRATION_OWNER unset)"
}
```

Point an external alert at this route if system emails matter to you. It is not part of
`/health/ready`, so a revoked mailbox never takes the server out of rotation.

## Which one to use

| Use | Route | Why |
| --- | --- | --- |
| Kubernetes liveness probe | `/health` | It must only prove the process is alive. Wired to the database, one slow query would restart healthy pods. |
| Kubernetes readiness probe | `/health/ready` | It keeps traffic away from a pod that cannot reach the database or has no key. |
| Docker Compose healthcheck | `/health` | The bundled `docker-compose.yml` uses it to order the services. |

The Helm chart is wired exactly this way:

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8000
  periodSeconds: 15
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8000
  periodSeconds: 10
```

The chart also sets a startup probe on `/health` (every 5 seconds, up to 30 times), so a slow
first boot is given up to 150 seconds before the liveness probe starts judging it.

The routes live on the backend. In the chart's default layout the Ingress publishes only the
frontend, so an uptime monitor pointed at `https://<host>/health` gets the frontend's `404`.
See [the Helm chart page](/deployment/helmchart) for what to monitor from outside.
